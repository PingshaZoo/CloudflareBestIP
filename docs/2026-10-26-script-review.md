# QwenGetBestIPs.py 修复与回归说明

本次保留现有历史优结果优先、两阶段探测、上报格式及可选阿里云 DNS 同步流程。
延续工作区已有的全局选优方向，最终结果按实际下载速度取 `TOP_N`，不再直接切片线程完成顺序。

## 已修复的问题

1. `_rank_by_speed` 原来只给临时列表赋分，没有排序最终列表；未测速的延迟分还可能排在速度达标节点之前。
2. TOP 固定取前 9 个，忽略 `TOP_N`；现在仅选择测速达标的节点。无达标结果时不调用 DNS 更新。
3. `worker` 早停时重复调用 `task_done()`；现在每个任务和结束哨兵只确认一次。
4. 第二阶段错误地把全局完成数与本阶段批次数比较，可能提前取结果；异常任务还可能使计数等待无法结束。改用每批 `queue.join()`。
5. 第一阶段已有 20 个达标结果时仍执行第二阶段；第一阶段全量测速也未计入早停计数。现已统一。
6. 重复测速会重复累计达标数；现在记录每个结果的测速状态，失败结果也不会被隐式反复重试。
7. `ttfb_ms` 原来包含完整文件下载时间，延迟计算遗漏 TLS 耗时。现在记录实际收到第一个字节的时间，延迟为 TCP + TLS + TTFB。
8. 原始 socket 解析可能没有读完 trace 正文就发送下一个请求。改用标准库 `http.client.HTTPResponse`，完整消费 trace 后复用连接；服务端关闭连接时重连。
9. HTTP 3xx 被视为成功，下载字节包含响应头，chunked 分块标记也可能被计入。现在仅接受 200，按解码后的正文计量，拒绝空、意外截断和压缩的测速响应。
10. 收包阻塞可能绕过 10 秒检查；现在每次底层读取都应用剩余截止时间。10 秒限制针对 HTTP 测速采样，不包括此前 TCP/TLS/trace。
11. TCP/TLS 成功数原来只在 HTTP 成功后累计，导致 HTTP 故障被记成 TCP/TLS 故障；完全失败和应淘汰的节点仍被保留。现在分层计数并实际丢弃。
12. 速度阈值在代码、日志和注释中不一致；现在早停、排名、TOP/DNS 全部以 `LOWEST_SPEED` 为准，等于阈值也达标。
13. 空 IP 源列表导致零线程池异常；历史结果中的非字典行、字符串、空值及 NaN 速度可能影响整批结果。现按行校验并规范化。
14. 历史 IP 绕过 CF 网段过滤；现在所有候选来源均过滤，规则无法加载且无有效后备配置时不接受未验证 IP。
15. curl POST 默认把 HTTP 4xx/5xx 也当成成功；已增加失败状态检查和超时。DoH 现在也能通过 urllib 回退，不强制依赖 curl。
16. 域名源失败会退出整个程序，即使还有可用 IP；现在允许其他来源继续工作。
17. 同一进程再次执行 main 会残留已测 IP、早停、计数和 colo；现在启动时清理运行状态。

## 性能改进

- 延迟探测只接收响应头，不再完整下载测试文件；下载流量集中在速度复测阶段。
- 复用只读 TLS 上下文，避免每个探测样本反复加载根证书；加载成本不计入 TLS 握手时间。
- 历史、第三方、域名数据源并发获取；CIDR 缓存初始化加锁避免并发重复下载。
- 内存 CIDR 匹配直接稳定去重过滤，移除逐 IP 建立 Future 的开销。
- 其他区域的节点可以补足增量测速候选，避免仅有欧美以外区域时不做速度复测。

## 参考与限制

实现前检索并通过国内镜像克隆了 [XIU2/CloudflareSpeedTest](https://github.com/XIU2/CloudflareSpeedTest)，
阅读其 README、目录、下载测速实现及相关 issue。该项目为 Go 程序，无法少量改动直接替代本项目的 Python 接口和 DNS 流程；
这里只参考状态码校验、正文计量和速度排序原则，没有复制其源码或引入依赖。

当前速度仍代表“本机经指定 CF IP 到配置源站”的结果，会受源站带宽和链路影响。
第一阶段仅测首字节；正文吞吐能力由第二阶段采样验证。HTTP 采样速度按正文 KB（1024 字节）除以请求到采样结束的秒数计算，含首字节等待。
默认增量测速仍是每 100 个 IP 中选至多 15 个候选，不是对全部 IP 的穷举测速；因此 TOP 是本轮已测速候选中的最优结果。
